Integration guide for partner websites

TOURISE 2027 — Partner API

Request an Invitation & Newsletter · updated 26 September 2026

Two endpoints behind one key: file an invitation request, and subscribe someone to the newsletter. Your website hosts its own forms and sends the results to TOURISE. A request filed this way lands in the same review queue as one filed on the TOURISE site, under the category you were given.

It is a single JSON POST. There is no SDK to install and nothing to embed.

Three things TOURISE gives you

API base URLhttps://<api-host>/api
Category sluge.g. press
API keytri_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

The key is shown once when it is issued. If it is lost, TOURISE issues a new one — that is also how it is rotated.

No backend of your own? Start here

Four ways to connect, from no code at all to a key in the browser. Pick one deliberately: an API key placed in browser JavaScript is visible to anyone who opens DevTools.

A · Send people to the TOURISE formNo key, no code

Link or redirect to the form TOURISE already hosts. Nothing to build, no key to hold, and every rule stays with us: required fields, the email verification code when the category asks for one, reCAPTCHA, and the reply email.

https://register.tourise.com/en/request-an-invitation/press
                            ^^                       ^^^^^
                            language (en / ar)       your category slug

Open it in a new tab from your own "Request an invitation" button. This is the whole integration.

Not in an iframe

The TOURISE site refuses to be framed (frame-ancestors 'none'), so an embedded window stays blank. Link or redirect instead.

B · Call it from a small server-side functionRecommended for your own form

Your form posts to your own endpoint; that endpoint adds the key and forwards it to TOURISE. One file on Vercel, Netlify, Cloudflare Workers or any host you already use. The key never reaches the browser, and there is no CORS setup at all.

C · Put the key in the browserAcceptable, with eyes open

Works today. Treat the key as public and understand the blast radius:

  • The key can only create a pending request. It cannot read, list, edit, accept or reject anything, and it reaches no other part of the system.
  • It is rate limited to 60 requests per minute per key.
  • Worst case if it is copied: junk requests in the review queue. TOURISE revokes the key and issues a new one.
  • Requests filed this way skip the email verification code, so nothing proves the address is real — see Email verification.

Requires your exact origin on the API's allow-list — see CORS.

D · The newsletter box, with no keyNewsletter only

POST /api/newsletter/subscribe takes a Google reCAPTCHA token instead of a key, which suits a page that can hold no secret. It needs TOURISE to share a site key registered for your domain. Invitation requests have no such route — that endpoint always requires a key, so use A, B or C for them.

Step 1 — Read the field list

GET/api/request-an-invitation/{slug}· public, no key needed

Tells you which fields to render and which to require, so your form follows the category without a redeploy when TOURISE changes it.

{
    "status": "success",
    "data": {
        "slug": "press",
        "name_en": "Press",
        "with_email_otp": true,
        "mandatory_fields": ["first_name", "company"]
    }
}

null means the category is not configured — nothing beyond email is required. with_email_otp says whether the TOURISE form asks for an emailed code; see Email verification.

Step 2 — File the request

POST/api/request-an-invitation/{slug}· key required
POST /api/request-an-invitation/press
X-Api-Key: tri_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Content-Type: application/json

{
    "email": "sara@example.com",
    "first_name": "Sara",
    "last_name": "Idris",
    "company": "Partner Co",
    "job_title": "Editor"
}

Authorization: Bearer <key> is accepted as the same credential if that header is easier for your HTTP client.

Success

HTTP 201   { "status": "success", "data": { "id": "01a0…", "duplicate": false } }

email is always required. Everything else is required only if the category says so, and the list in Step 1 is the live answer — it follows the category without a redeploy. Any field not on that list is ignored.

Countries are UUIDs

country_of_residence and nationality take the id from GET /api/countries — not "Saudi Arabia". Fetch that list once and use it to populate your dropdowns.

Responses

CodeMeaning · what to do
201Filed. Show your thank-you.
200Already pending for that address — duplicate: true, nothing new created. This is a success. Show the same thank-you; it stops a double submit putting one person in the queue twice.
401Key missing, unknown or revoked. Not retryable — contact TOURISE.
404No category at that slug. Check your spelling of the slug.
410The category exists but is closed. Stop showing the form and say applications have closed.
422Validation failed. errors names each field — show them against your inputs.
429Rate limited (60/min per key). Back off and retry.
Treat 200 and 201 the same

Both mean the person is in the queue. Only 4xx is a failure worth showing the user an error for.

Email verification (OTP)

A category can ask applicants to prove the address they typed, by entering a code emailed to it. Whether that applies to you depends on how you integrate.

How you file the requestDoes the code apply?
The TOURISE form (option A)Yes, when the category has it on. We send the code, check it and file the request. Nothing for you to build.
The partner API with your key (B or C)No. The code is skipped, whatever the category says. Your key is the trust, and there is no inbox of the applicant's for your server to read. An otp_token sent with a key is ignored.

What it looks like on the TOURISE form

Turned on per category in the TOURISE admin, and reported to you as with_email_otp in Step 1:

  1. The applicant types their email and asks for a code.
  2. TOURISE emails an 8-character code. Only one code is live per address — asking again replaces the previous one.
  3. They type it back. The code is checked against the address it was sent to, so a code obtained for one address cannot file a request under another.
  4. The request is filed, and the code is spent. A second request needs a fresh code.

If you want the same proof on your own form

You can run the two calls behind it yourself. Both need a Google reCAPTCHA token, so TOURISE has to share a site key registered for your domain first — ask before you build this.

POST/api/guests/email-verification· sends the code
{ "email": "sara@example.com", "recaptcha": "<token>" }
POST/api/guests/email-confirmation· checks it
{ "token": "A1B2C3D4", "recaptcha": "<token>" }

// 200 → { "status": "success", "token": "A1B2C3D4" }   the code is good
// 404 → { "status": "failed", "error": "wrong token" }

Both share a site-wide ceiling of 300 calls a minute, because each one spends a real email.

It proves the address, not the person

Filing with your key still skips the check on our side, so treat this as your own front-door validation. If you would rather the verification were ours, send people to the TOURISE form (option A).

After the request is filed

Who talks to the applicant next, and what each side keeps.

What TOURISE sends them

MomentWhat we sendWhen nothing goes out
Filed (201)A holding email — it arrived and is waiting on a decision.Only if the category names a template for it. Otherwise the applicant hears nothing yet.
Duplicate (200)Nothing. The earlier request still stands.Always — a second submit sends no second email.
AcceptedTheir invitation, with the link to register, on the channel that category uses.—
RejectedA rejection email.Only if the category names a template. Otherwise the request is closed silently.
Ask before you word your thank-you

Whether the holding email exists is a setting on your category, not a promise of the API. Ask TOURISE which of the four above are switched on for you. If there is no holding email, do not write "check your inbox" — say the request was received and they will hear when it is reviewed.

What TOURISE keeps

The request row: the fields you sent, the language, which partner site filed it, its status, and the reviewer's note. A newsletter opt-in is kept separately as a subscriber, attributed to your site the same way. Nothing else about the visitor reaches us — we see no page views, no cookies and no IP from your site.

What you keep

Whatever you choose: the API needs no copy on your side, and the review queue is the record TOURISE works from. If you do keep one, say so in your own privacy notice — it is your form and your visitor. An applicant asking to be removed from the TOURISE queue should be passed to your TOURISE contact; you cannot delete through this API.

Example — browser (option C)

// The key is visible to anyone who opens DevTools. See option B.
const res = await fetch(`${API_BASE}/request-an-invitation/press`, {
    method: 'POST',
    headers: {
        'Content-Type': 'application/json',
        'Accept': 'application/json',
        'X-Api-Key': API_KEY,
    },
    body: JSON.stringify({
        email: form.email,
        first_name: form.firstName,
        company: form.company,
    }),
});

const body = await res.json();

// 200 = already pending, 201 = created. Both are a success.
if (res.ok) return showThankYou();

if (res.status === 422) return showFieldErrors(body.errors);
if (res.status === 410) return showClosedMessage();
return showGenericError();

Example — server-side function (option B)

// /api/request-invitation — Vercel / Netlify / Cloudflare function.
// The key stays here and never reaches the browser.
export default async function handler(req, res) {
    const upstream = await fetch(
        `${process.env.TOURISE_API_BASE}/request-an-invitation/press`,
        {
            method: 'POST',
            headers: {
                'Content-Type': 'application/json',
                'Accept': 'application/json',
                'X-Api-Key': process.env.TOURISE_API_KEY,   // server-side only
            },
            body: JSON.stringify(req.body),
        }
    );

    const body = await upstream.json();
    res.status(upstream.status).json(body);
}

CORS

Only matters for option C. A browser refuses the call unless your exact origin is on the API allow-list. Send TOURISE the origins you post from, including scheme and any subdomain:

https://www.yourdomain.com
https://yourdomain.com
https://staging.yourdomain.com

Posting from your own server (option B) needs none of this — CORS is a browser rule and does not apply. Linking to the TOURISE form (option A) needs none of it either.

Before you go live

  1. GET the field list and confirm your form asks for everything in mandatory_fields.
  2. Submit once and confirm you get 201.
  3. Submit the same address again and confirm you get 200 with duplicate: true — and that your UI treats it as success, not an error.
  4. Submit with a missing required field and confirm you render the 422 errors against the right inputs.
  5. Submit with a deliberately wrong key and confirm you get 401 and show a sensible message.
  6. Check with_email_otp: if it is true and you file with a key, decide how you verify addresses yourself.
  7. Ask TOURISE to confirm the request appeared in the review queue.
  8. Option C only: confirm your production origin is on the CORS allow-list.

Good to know

  • Submitting is a request to be reviewed — not a registration and not a confirmed place. Say so on your form, or applicants will expect a ticket.
  • TOURISE records which partner site filed each request, so your submissions are attributed to you automatically. You do not send that.
  • The rate limit is per key, so another partner cannot use up your budget.
  • Nothing here needs Google reCAPTCHA, unless you run the email verification calls yourself or use the keyless newsletter route.

Newsletter signup

The same key, for a signup box on your site.

POST/api/newsletter/subscribe
POST /api/newsletter/subscribe
X-Api-Key: tri_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Content-Type: application/json

{
    "email": "sara@example.com",
    "first_name": "Sara",
    "last_name": "Idris",
    "company": "Partner Co",
    "lang": "en"
}

Only email is required. New subscribers join the default list automatically. A page that can hold no secret may send recaptcha instead of the key — a wrong key is still refused, so send one or the other.

Say the right thing back

Success is always 201. Read state — "Thanks for subscribing" shown to someone who signed up months ago reads as though the first time never took.

stateMeaningSay
subscribedNew — now on the list"Thanks for subscribing"
already_subscribedWas already on the list"You are already subscribed"
resubscribedHad unsubscribed, now back"Welcome back"

401 for a missing, unknown or revoked key. 422 if the address is not a valid email.

About the token field

token comes back only when state is subscribed — a genuinely new address. It is a bearer credential: whoever holds it can read that subscriber and unsubscribe them, so it is never returned for an address that already existed, where the caller may know the address without owning it. Do not build a flow that needs it back for an existing subscriber.

Attribution

TOURISE records which partner site each subscriber came from, taken from your key rather than anything you send. The first site to subscribe an address keeps the attribution — a later signup elsewhere does not rewrite where they originally came from.
