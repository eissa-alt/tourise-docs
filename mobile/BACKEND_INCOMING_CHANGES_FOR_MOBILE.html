Auth header

Authorization: Bearer <sanctum-token>
Accept: application/json
Accept-Language: en          # or 'ar'
X-Requested-With: XMLHttpRequest    # optional but recommended
Sanctum header is tolerant. See app/Providers/AppServiceProvider.php::boot() — the server accepts Bearer X, bearer X and a raw token without any prefix. Flutter http sometimes lowercases bearer on retries; this is handled.

Locale resolution

app/Http/Middleware/Localization.php: ?lang= query param wins over Accept-Language header. Only ar sets Arabic; anything else (including missing) is treated as en. Resources fall back from *_ar to *_en when the AR field is blank.

Error responses

OTP rules & lifecycle

  • 6-digit numeric, generated with rand(100000, 999999) — not cryptographically random (acceptable per spec; OTP is short-lived + rate-limited).
  • email_verifications table holds one row per email (upsert on each check-email call). Both wrong OTP and successful verify clear or update the row.
  • Sanctum token TTL: MOBILE_TOKEN_EXPIRY_DAYS (default 30 days), per-token expiry via createToken('mobile', ['*'], now()->addDays(...)).
  • OTP delivered by GuestOtpMailable (Mailtrap in testing, prod uses configured SMTP).

Edge cases / gotchas

  • Deletion stealth: a guest who has filed delete-account returns the same "not registered" 400 as if they never existed. Mobile must NOT special-case it.
  • OTP attempts counter: a wrong OTP increments attempts but does NOT delete the row. Once threshold is hit, only a fresh check-email resets it (because updateOrInsert resets attempts to 0).
  • Demo account bypass (§7) skips the entire OTP flow — be sure to not log/store the literal demo OTP.
  • Throttle: sensitive-api rate limit applies to check-email + verify-otp — bursty retries will return 429 from Laravel's throttler (no JSON body).
  • Token does NOT auto-refresh: when 30-day TTL hits, the next call returns 401. Mobile must catch 401 and route to the OTP screen.

Code & files

  • app/Http/Controllers/MobileAuthController.php (lines 21-251) — all 5 endpoints.
  • config/mobile.php — env-driven knobs (OTP TTL, max attempts, token TTL, demo creds).
  • app/Mail/GuestOtpMailable.php — locale-aware OTP email.
  • tests/Feature/MobileAuthTest.php (510 lines) — full coverage including throttle, deletion stealth, demo bypass.

5. F1b — Device token registration (FCM / APNs / HMS) New

MethodPathBodyNotes
POST /api/mobile/identity/device-tokens { token: string, platform?: "fcm" | "apns" | "hms" } idempotent on (guest_id, token) (unique constraint); platform defaults to "fcm"

Why & when mobile must call this

  • Right after a successful verify-otp (or demo-otp) so push starts working immediately.
  • On every FCM/APNs token refresh callback (token can rotate at any time).
  • After the user grants OS push permission for the first time.
  • On logout: do NOT delete the token server-side — the table is global per guest, deletion happens automatically when FCM reports UNREGISTERED (handled by FirebaseNotificationService::isUnregistered). If the user logs in again on the same device, the unique constraint makes re-upsert a no-op.

Request / response

# request
POST /api/mobile/identity/device-tokens
Authorization: Bearer 1|xxx
{
  "token": "eYf...fcm_token",
  "platform": "fcm"
}

# 200 OK
{
  "message": "Device token registered successfully.",
  "user": { … GuestMobileResource … }
}
If this call is missed, the user receives no push notifications for chat, room booking, or admin notifications — the rest of the app continues to work, so this is silent failure on the surface. Add it to the post-login critical path.

Code & files

  • app/Http/Controllers/MobileAuthController.php::registerDeviceToken (line 259).
  • app/Models/DeviceToken.php — UUID PK, foreign to guests, cascade delete, unique on (guest_id, token).
  • Migration: 2026_04_21_000001_create_device_tokens_table.php.

6. F21 — Account deletion (Apple Review) New

MethodPathEffect
GET /api/mobile/identity/delete-account Inserts row in account_deletion_requests, revokes EVERY Sanctum token for the guest (all devices logged out), and invalidates any pending OTP.

Response

{ "message": "Account deletion requested. You have been logged out." }

What happens next (server side)

  1. Future check-email calls return the "not registered" message (stealth — Apple compliance).
  2. Admin sees the request in /admin/account-deletion-requests and hard-deletes the guest row.
  3. FK guest_id on device_tokens, chat pivots, registrations etc. cascade-delete with the guest.
Mobile UX requirements (Apple Review):
  • Reachable from Settings within 1-2 taps.
  • Gated behind features.delete_account from app-config (§8).
  • Confirmation dialog must use the word "permanent" or "irreversible" and a destructive (red) CTA.
  • On 200 response, clear all local state (token, cache, settings) and route to the login screen.

8. F5 — App config & white-label theme New public

MethodPathPurpose
GET/api/app-config/versioncheap poll → { version: "abc123..." }
GET/api/app-configfull themed payload (both EN+AR)

Lifecycle

  1. Admin saves Conference → AdminConferenceController::createOrUpdate regenerates a config_version = Str::random(16), then calls Cache::forget('app_config') and Cache::forget('app_config_version').
  2. Mobile polls /app-config/version on app start / resume / interval.
  3. If returned version != cached one, mobile fetches /app-config and stores both.
  4. Server caches both endpoints forever until the next admin save busts them.

Color format

All theme colors are hex strings of length 7 (#RRGGBB) or 9 (#RRGGBBAA). Regex enforced server-side: /^#[0-9a-fA-F]{6}([0-9a-fA-F]{2})?$/. null means "use built-in fallback".

Feature flags

All 14 flags are nullable booleans. null = "not configured yet" — mobile should treat as off. The flags are properly cast to PHP booleans (protected $casts on Conference.php), so Flutter receives JSON true / false / null, never 0 / 1.

Edge cases / gotchas

JSON-object vs array contract. feature_labels, feature_icons and navigation MUST always serialize as JSON objects ({}). Backend has two safeguards:
  1. AdminConferenceController validates with $mapShapeRule and rejects indexed arrays with 422.
  2. AppConfigController casts empties back to (object)[].
Flutter must deserialize as Map. If you ever see [], something bypassed the controller — please file a bug.

Recommended client flow

  1. On app start (cold) and on resume → call /app-config/version.
  2. If version != cached → fetch /app-config and store both.
  3. Drive every feature toggle and theme color off the cached payload — never hard-code.
  4. Suggested polling cadence: app start + resume + every 30 min while foreground.

Room visibility — IMPORTANT

Slot booking — race safety

MobileRoomController::book uses an atomic single-statement UPDATE: WHERE id = ? AND is_booked = false. Whichever request matches 1 row wins; the rest match 0 rows and get a 400. No transaction needed; no deadlock risk.

How fan-out works (server side)

  1. Admin POSTs /api/admin/notifications with { title, message, priority?, category_id? }.
  2. Server creates an app_notifications row and resolves target guests (Accepted/Invited, optionally narrowed by category_id).
  3. It sends FCM to every device-token of those guests via FirebaseNotificationService::sendToTokens (chunked at 500 per FCM multicast).
  4. It bulk-inserts notification_recipients rows (one per guest) in chunks of 1000.
  5. Updates the notification with status = Sent and sent_count.
Mobile must NOT change the verbs. All four endpoints are GET by design (matches Flutter's GetRequestStrategy which wraps these calls and parses "OK" / integer responses literally). The body of mark-read and clear is a literal string, not JSON. unread-count body is a literal int.

Channel authorization (server side)

// routes/channels.php
Broadcast::channel('chat.{roomId}', function ($user, string $roomId) {
    if (! $user instanceof Guest) return false;
    return ChatRoom::where('room_id', $roomId)
        ->whereHas('participants', fn ($q) => $q->where('guest_id', $user->id))
        ->exists();
});

FCM push on send

After persisting the message, the controller fans it out to every DeviceToken belonging to the recipient. FCM failure is non-blocking — a Firebase outage never causes the message to be lost.

Mobile integration sketch (Flutter, pusher_channels_flutter)

final pusher = PusherChannelsFlutter.getInstance();

  apiKey: REVERB_APP_KEY,
  cluster: '',
  useTLS: true,
  host: 'pif-mobile-api.registration-panel.com',
  wsPort: 443, wssPort: 443,
  authEndpoint: 'https://pif-mobile-api.registration-panel.com/broadcasting/auth',
  onAuthorizer: (channel, socketId, _) async {
    final res = await http.post(authUrl, headers: {
      'Authorization': 'Bearer $sanctumToken',
    }, body: { 'channel_name': channel, 'socket_id': socketId });
    return jsonDecode(res.body);

Edge cases / gotchas

  • The sender does NOT receive their own broadcast — they got the message back from the HTTP response. UI must immediately add the message from the response.
  • Marking-as-read happens when /messages is fetched — it is NOT triggered by receiving a broadcast. If the user is sitting on the chat screen and a new message arrives via WSS, you must either refetch /messages or send a read receipt yourself (none built-in yet).
  • Channel authorization checks chat.{roomId} — note the channel name in the broadcast event is private-chat.{roomId}; Pusher's protocol strips the private- prefix when calling the channel auth callback. Don't worry — both Echo and pusher_channels_flutter handle this.
  • Reverb server must be running (php artisan reverb:start) — if it isn't, the HTTP send still succeeds but no WSS event is delivered. Mobile should treat REST as the source of truth and broadcast as an optimization.

Other conventions

  • Side-effecting GETs in F6 (mark-read, clear) are intentional. Do NOT refactor to PATCH/DELETE.
  • Empty maps in app-config are encoded as {}, never [].
  • Storage URLs are absolute — never reconstruct from a filename.
  • Localization fallback: *_ar falls back to *_en when blank.
  • Sanctum token is per-token expiring, not session-based. Caught 401 → re-login (no refresh endpoint).
  • Session / Workshop date is venue-local (Asia/Riyadh) Contract change 2026-07-07 — serialized as a naive YYYY-MM-DDTHH:MM:SS string with no Z / offset (previously UTC …Z via toISOString()). Parse it as a wall-clock time and display it as-is; do NOT convert to the device timezone (the value already is the event's local time). Affects SessionList/Detail, FavoriteSession, Workshop List/Detail, RegisteredWorkshop, and the nested sessions in Speaker. Audit fields (createdAt/updatedAt) and other timestamps are unchanged and remain UTC ISO 8601.

Local development tips

  • To test Reverb locally without TLS: set REVERB_SCHEME=http and REVERB_PORT=8080, run php artisan reverb:start, and point Flutter at ws://localhost:8080/app/dg-2026-key.

  • Use tests/Feature/MobileAuthTest.php as the canonical spec for the auth flow — every edge case is documented there.

Files / changes that surprised the reviewer

  • AppServiceProvider::boot overrides Sanctum's bearer-token extractor to accept lowercase / no-prefix tokens (Flutter quirk).
  • BroadcastServiceProvider::boot remounts Broadcast::routes on sanctum middleware — the default uses web and silently 403s API clients.
  • MobileRoomController::isSlotInPast uses start_time + slot date, not end_time — a slot that has started but not ended is still considered "past". UI should reflect this.
  • MobileChatController::messages marks read as an aggregate update on the whole room — NOT bound to the returned page. Paginating backward through history will mark already-read messages as read again (no harm).
  • MobileAuthController::checkEmail returns 200 success even if the guest doesn't actually receive the email — the OTP is upserted regardless. If email delivery fails (Mailtrap down etc.), Flutter sees success but no code arrives. Consider adding a "Resend OTP" CTA after 30 s.
